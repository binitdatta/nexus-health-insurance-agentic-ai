Security, Privacy & Compliance Architecture

HIPAA Compliance & AI Risk Posture

This page documents architectural controls, known gaps, contractual dependencies, and deployment alternatives for the Nexus Health Insurance Agentic AI Platform.

This is not a HIPAA certification and is not legal advice. HIPAA compliance is an organizational responsibility involving technical safeguards, administrative safeguards, physical safeguards, contracts, policies, risk analysis, workforce practices, monitoring, and ongoing governance.

CURRENT POSTURE: DO NOT PROCESS REAL PHI YET

The current development configuration contains unresolved controls that must be addressed before this platform should process production electronic Protected Health Information (ePHI).

Key examples include the third-party BAA scope, application-to-application TLS, database encryption, audit-log protection, and minimum-necessary data handling.

Executive View

What HIPAA Means for This AI Architecture

A technically sophisticated LLM architecture can still create serious compliance exposure if contracts, PHI handling, logging, encryption, access, or operational governance are incomplete.

Identity Matters

Keycloak provides a strong foundation for identifying users and enforcing department boundaries, but identity alone does not make the platform compliant.

Contracts Matter

If an external service receives ePHI as a business associate, appropriate contractual coverage must be in place before production PHI is disclosed.

Data Location Matters

PHI can exist not only in business tables but also in prompts, retrieved context, responses, HTTP logs, LLM logs, backups, exports, and monitoring systems.

Operations Matter

Patching, incident response, access review, key rotation, retention, backups, workforce procedures, and risk analysis remain ongoing responsibilities.

The Issue No Architecture Can Fix by Itself: The Business Associate Agreement

A Business Associate Agreement is a contractual/legal prerequisite when a third-party business associate will create, receive, maintain, or transmit PHI on behalf of the covered entity or another business associate.

Therefore, excellent authentication, encrypted databases, network segmentation, audit logging, and secure coding do not independently authorize PHI disclosure to an external LLM provider.

For Anthropic, the organization must verify its own current contractual relationship, the HIPAA-ready configuration actually enabled, and the exact API features and tools covered by its signed agreement. Do not infer coverage merely because a provider advertises HIPAA-capable services.

This platform relies heavily on structured / forced tool-use. That capability must therefore be included within whatever contractual and technical configuration is approved for production use.

Deployment Gates

Do Not Process Production PHI Until These Are Resolved

These controls should be treated as release gates, not items to address after production deployment.

1. Confirm Contractual Coverage
Verify the signed BAA and approved service configuration for every third party that will create, receive, maintain, or transmit ePHI. Confirm the exact LLM API capabilities in scope.
2. Encrypt Every Production Network Path
Browser, chatbot, Keycloak, Gateway, database, management interfaces, log collectors, backups, and administrative connections must use approved encrypted transport.
3. Protect ePHI at Rest
Protect primary database storage, snapshots, backups, exports, log stores, temporary files, object storage, and any other persistence layer that may contain ePHI.
4. Treat AI Logs as PHI-Capable Data Stores
Prompts and model responses can contain the same sensitive information as production business tables. Logging must therefore follow equivalent access, encryption, retention, and monitoring controls.
5. Implement Minimum-Necessary Context
Do not send complete database rows to an LLM merely because they are convenient to retrieve. Select only the attributes necessary to perform the current authorized operation.
6. Establish Production Secret and Key Management
API credentials, signing keys, database passwords, encryption keys, Keycloak secrets, and certificates require managed storage, controlled access, rotation, revocation, and auditability.
7. Define Data Retention and Secure Disposal
Establish explicit retention periods for chat transcripts, prompts, responses, HTTP logs, LLM logs, HITL records, backups, and exported reports.
8. Establish Incident Response and Breach Procedures
Technical logging is useful only if the organization also defines who investigates suspected exposure, how access is revoked, how evidence is preserved, and how legal/privacy teams are engaged.
9. Complete Formal Security Risk Analysis
Architecture review is not a substitute for an organizational HIPAA Security Rule risk analysis. Risks, likelihood, impact, controls, owners, and remediation decisions should be formally recorded.
AI-Specific Risk

Where PHI Can Appear in an LLM Application

Protecting the source database is not enough. AI applications create additional copies and representations of sensitive information.

1
Retrieved Context

Business rows and knowledge documents selected by RAG can contain member identifiers, clinical data, financial data, notes, and other sensitive information.

2
Prompt Construction

Retrieved PHI may be combined with user questions, instructions, system prompts, and tool schemas before being sent for inference.

3
Model Responses

A response can reproduce or transform PHI even if the application never explicitly stores the original database row.

4
Operational Logging

Logging complete prompts and responses can unintentionally create a second large PHI repository outside the department domain table.

5
HITL Drafts

Human-review queues can persist model-generated records containing PHI and therefore require appropriate authorization and lifecycle controls.

6
Telemetry and Troubleshooting

Debug traces, exception logs, screenshots, support tickets, APM tools, exports, and developer diagnostics can become secondary disclosure paths.

Deployment Strategies

Three Approaches

These choices primarily change where inference occurs and who operates the model. None eliminates the organization's HIPAA responsibilities.

Approach A
Managed API + Signed BAA

Use Anthropic's API under an appropriately executed HIPAA-ready contractual arrangement covering the specific capabilities this platform uses.

Lowest operational burden — no GPU fleet or model hosting.
Strong model capability for structured tool-use.
Contractual coverage must be confirmed and kept current.
Usage remains subject to external-provider pricing and approved-service constraints.
Approach B
Self-Hosted Open Model

Run an open-weight model such as Llama or Qwen through Ollama or another inference stack in a controlled computing environment.

Model inference can remain inside infrastructure controlled by your organization.
Infrastructure cost can be more predictable than per-token pricing.
You inherit model-serving security, patching, monitoring, availability and capacity obligations.
Tool-use reliability must be independently tested.
Important: self-hosting the model does not necessarily remove all BAA requirements. A cloud/IaaS provider storing or processing ePHI may itself be part of the HIPAA business-associate chain.
Approach C
Hybrid: Minimize + Managed API

Tokenize identifiers, reduce free text, select intent-specific fields, and use the managed API under appropriate contractual coverage.

Reduces unnecessary disclosure of PHI.
Fits naturally with this platform because retrieve_node already knows the user intent.
Clinical and resolution notes can be difficult to redact safely and consistently.
Minimization is defense-in-depth, not a substitute for required contractual protection.
Minimum Necessary Should Be an Architectural Rule

Today, retrieval can return a complete row and forward that entire row to the LLM. A production design should instead determine which fields are actually required for the user's specific intent.

For example, a question about claim status may require claim number, status, date and reason code — but not a full clinical-note field merely because that column is present in the same table.

Better pattern
intent allowed fields
rather than
SELECT * LLM

Self-Hosting Does Not Mean "HIPAA Problem Solved"

Moving the model inside your own environment can remove one external LLM-provider dependency, but it makes your organization directly responsible for substantially more of the operational security stack.

GPU host hardening
OS and driver patching
Container / inference-runtime security
Network segmentation
Identity and administrative access
Model artifact provenance
Vulnerability management
Capacity and availability
Encryption and key management
Monitoring and incident response
Human-in-the-Loop Is an Important Safety Control

This platform already contains an important control: AI-generated create/update operations are drafted before they are committed. The user can inspect, edit, approve, or reject the proposed record.

That reduces autonomous-write risk, but the HITL workflow itself must still enforce user authorization, maintain audit history, protect any PHI inside the pending task, and prevent unauthorized reviewers from approving another department's proposed action.

Final Architectural Principle

HIPAA Compliance Is a System Property, Not an LLM Feature

Keycloak, TLS, encryption, a BAA, RAG minimization, HITL, audit logging, self-hosted models, and secure databases are individual controls. None should be presented as "HIPAA compliance" by itself. The compliance posture emerges from the complete technical, administrative, contractual, and operational system—and from how that system is continuously governed.

Production decision:
Process real PHI only after the responsible security, privacy, compliance, legal, and business owners formally accept the architecture and its residual risks.
