RBAC for AI Agents: Department-Scoped Access Control with JWT Claims

Understand authentication vs. authorization.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Learning Objectives
Understand authentication vs. authorization.
Use signed JWT claims as inputs to authorization decisions.
Explain why request-supplied dept_code cannot be trusted by itself.
Understand defense-in-depth checks across chatbot and Gateway boundaries.
Authorization Model
Keycloak authenticates the user and issues a signed token.
A department attribute/claim identifies the user organizational scope.
The chatbot validates the token in the context of its own client.
The Gateway independently compares the signed department claim with the requested department.
A mismatch is rejected even if the user is otherwise authenticated.
Why This Matters for Agents
Agentic systems can call tools and retrieve data on behalf of users.
The agent must never become a way to bypass the user authorization envelope.
Tool permissions, database access, retrieval scope, and HITL approval must all remain bounded by authenticated identity.
Negative Testing
Test Claims token against Claims: accept.
Test Claims token while requesting Billing scope: reject.
Test malformed/expired tokens: reject.
Test missing department claim: reject or fail closed according to policy.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
