Keycloak 26 PKCE for Enterprise AI Chatbots (with a Real Bug I Found)

Explain Authorization Code + PKCE for server-rendered Flask applications.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Learning Objectives
Explain Authorization Code + PKCE for server-rendered Flask applications.
Understand why public-client PKCE avoids embedding a client secret in the browser-facing login flow.
Understand department claims, azp validation, audience checks, and user-token relay.
Recognize why authentication success is not enough without authorization checks at each service boundary.
Token Relay Pattern
The user signs in to a department chatbot through Keycloak.
Keycloak issues a signed access token carrying the user identity and department context.
The chatbot relays that same user token to central-llm-gateway rather than replacing the user with a generic machine credential.
The Gateway compares the token department claim with the request dept_code.
The chatbot independently validates the token authorized-party context against its own client.
Why Separate Department Clients Matter
Claims, Billing, Finance, Nursing, and the other applications have distinct trust boundaries.
A valid token for one application should not automatically become valid for another department application.
Negative tests are as important as successful-login tests: a Claims identity must be rejected when presented as Billing.
Real-World Bug Lesson
OIDC/PKCE implementations often fail because of state/session handling, redirect URI mismatches, or library-version behavior rather than because the OAuth specification itself is wrong.
Test the complete browser round trip, not only token decoding in isolation.
Record the exact failure mode and regression-test it so it does not return during later refactoring.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
