Real Bugs I Found Testing an LLM-Backed Enterprise App (Not Hypotheticals)

LLM-backed applications still fail because of dependency versions, sessions, SQL, authentication, serialization, environment drift, and packaging.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Why This Topic Matters
LLM-backed applications still fail because of dependency versions, sessions, SQL, authentication, serialization, environment drift, and packaging.
Model quality does not compensate for broken deterministic infrastructure.
Every chatbot should be tested with real seeded data and real signed identity tokens.
Classes of Bugs to Expect
Dependency/version pinning failures.
Session mutation or OAuth state-handling mistakes.
SQL quoting and apostrophe problems that silently break scripts.
Incorrect department or client authorization assumptions.
Schema mismatches between model-generated fields and persistence code.
Packaging errors that appear only after a fresh install.
Testing Discipline
Run positive and negative authentication tests.
Test each department client independently.
Test retrieval with known seeded records.
Test create/update proposals without automatically committing.
Extract shipped packages into a fresh environment, reinstall dependencies, and rerun tests.
Core Lesson
Enterprise AI is still enterprise software. The LLM adds a probabilistic component, but the surrounding application must remain deterministic, testable, observable, and reproducible.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
