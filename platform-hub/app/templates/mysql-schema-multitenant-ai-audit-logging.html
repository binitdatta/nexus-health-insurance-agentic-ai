Data Architecture

Designing a MySQL Schema for Multi-Tenant AI Audit Logging

departments: tenancy/department anchor.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Core Tables
departments: tenancy/department anchor.
app_users: application representation of Keycloak identities.
10 department domain tables: transactional business data.
knowledge_docs: department-scoped RAG content.
llm_call_log: model request/response, token, latency, and cost metadata.
http_call_log: chatbot-to-Gateway call audit.
hitl_task_queue: AI-drafted proposals and human review outcomes.
cost_summary_daily: pre-aggregated reporting.
Department Scoping
Shared tables should carry dept_id or another explicit department key where appropriate.
Every query must deliberately apply department scope; a shared database does not imply shared authorization.
Identity and department values used for audit should come from trusted authenticated context rather than user-editable form values.
AI Audit Logging Risks
Full prompts and responses can contain PHI or other sensitive business data.
Operational logs may become a second sensitive database.
Retention, access, encryption, and export controls should be applied to AI logs with the same seriousness as domain tables.
Performance and Reporting
Daily cost summaries avoid re-aggregating raw high-volume LLM logs on every dashboard request.
Indexes should support department, user, request ID, timestamp, status, and correlation queries needed for operations and investigations.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
