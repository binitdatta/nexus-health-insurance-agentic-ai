Platform Architecture

Nexus Health Insurance AI Platform

A department-oriented AI architecture in which ten independently operated healthcare chatbots share centralized identity, controlled LLM access, and a common data platform while retaining their own business context and department boundaries.

The architecture is intentionally designed around a simple principle: centralize the capabilities that should be common — authentication, LLM connectivity, governance and platform logging — while keeping department-specific business behavior close to the department chatbot.

System Architecture
Reading the diagram: follow the architecture from top to bottom. Department users authenticate through the shared Keycloak realm, enter their own department chatbot, retrieve department-specific information, and use the Central LLM Gateway whenever an LLM operation is required. The Gateway provides the controlled outbound path to Anthropic.
One Identity Plane

One Keycloak 26 realm provides centralized authentication, while department-specific users, client registrations, claims and authorization boundaries distinguish the ten chatbot applications.

Ten Department Applications

Claims, Nursing, Billing, Finance and the other departments operate as independent Python Flask applications with their own ports, business context, retrieval behavior and LangGraph workflows.

One LLM Egress Path

Individual chatbots do not independently manage Anthropic connectivity. LLM requests are mediated through the central-llm-gateway on port 8000.

One Common Data Platform

MySQL 8 provides the shared physical database platform while department IDs, department-specific tables and knowledge_docs maintain logical separation.

How to Explain This Architecture

A useful way to present the platform is to describe it as six architectural layers. Each layer solves a different problem.

1
Access Layer

The starting point is the healthcare employee using a normal web browser.

Users do not enter one giant generic chatbot. They enter the chatbot belonging to their business function — for example Claims, Nursing, Billing or Finance.

2
Identity Layer

Keycloak 26 is the common authentication authority for the entire platform.

Authentication uses OAuth 2.0 / OpenID Connect with PKCE. Users remain distinguishable by department instead of every chatbot sharing one anonymous technical identity.

3
Application Layer

The platform contains ten separate Python Flask chatbot applications.

Each chatbot understands the vocabulary, transactional data, policies and workflows of its own department rather than forcing one application to understand every healthcare domain.

4
Shared Integration Layer

The Central LLM Gateway separates internal applications from the external LLM provider.

This creates one controlled integration point for authentication validation, request mediation, model access policy and consistent LLM-call behavior.

5
External LLM Layer

Anthropic provides the external large language model capability.

The enterprise applications do not need to know how every external model provider is accessed. That concern is abstracted behind the Gateway.

6
Data Layer

MySQL 8.x provides the common persistence platform.

It stores department business data, department-scoped RAG documents, user mappings, LLM-call information, HTTP-call information, HITL tasks and cost summaries.

End-to-End User Request Journey

A single user question crosses several trust and processing boundaries before a response is returned.

1
User enters the department application

A Claims employee opens the Claims chatbot, a Billing employee opens Billing, and so on.

2
Keycloak authenticates the user

The chatbot initiates an OIDC Authorization Code + PKCE flow. Keycloak authenticates the human and issues the signed token used by the application.

3
The chatbot interprets the request

LangGraph coordinates intent classification, retrieval, response synthesis and — when needed — preparation of a human-reviewable transaction.

4
Department retrieval happens locally

The chatbot queries only the business data and knowledge_docs relevant to its department. Retrieved information becomes controlled context for the subsequent LLM request.

5
The chatbot calls the Central LLM Gateway

The user token is relayed with the request. The Gateway verifies the request's department identity before allowing it to proceed.

6
The Gateway calls Anthropic

Anthropic receives the prompt and context through the one controlled outbound AI integration path.

7
The answer returns to the department chatbot

The chatbot presents the generated answer to the authenticated user and can continue the LangGraph workflow.

8
High-impact changes require a human decision

For create or update operations, AI proposes the action. A human reviewer approves or rejects the proposed transaction before the database is changed.

Authentication: User Token Relay

The design preserves the identity of the original human user all the way into the Gateway instead of replacing that user with a generic shared credential.

  1. The user signs into their department chatbot using PKCE.
  2. Keycloak issues a signed access token carrying the user's department information.
  3. The chatbot backend relays the same user token to the Gateway.
  4. The Gateway compares the token's department claim with the request's dept_code.
  5. The department chatbot independently checks the token's azp against its own Keycloak client ID.
Why this matters
A Claims identity cannot simply claim to be Billing. Identity remains attributable to the user and the department throughout the request path.
LangGraph Orchestration

LangGraph is used inside each department chatbot to coordinate application behavior rather than treating every interaction as a single prompt.

classify_intent retrieve synthesize hitl_draft
Node Responsibility
classify_intent Determines what kind of business operation the user is requesting.
retrieve Reads department-specific business and RAG data.
synthesize Uses the LLM to construct the contextual response.
hitl_draft Produces a proposed structured transaction for create/update use cases.

The key boundary is that retrieval belongs to the department chatbot. The Central Gateway is not the enterprise RAG engine.

RAG and Data Boundary
Retrieval stays inside the department application

The Gateway is deliberately prevented from becoming a giant cross-department data-access service.

A department chatbot retrieves the records and policy documents that it is authorized to use. It then sends only the context required for the current LLM operation to the Central LLM Gateway.

Important Boundary
Department chatbot: understands business tables and knowledge_docs.
Central Gateway: understands LLM requests, authentication context and AI-provider interaction.
Why the Central LLM Gateway Exists

Without the Gateway, every department chatbot would become its own independent AI integration. That would spread model credentials, provider-specific code and governance rules across ten different applications.

Credential Isolation

External LLM connectivity can be managed centrally rather than copied into every chatbot.

Policy Enforcement

Department identity can be verified before requests are allowed to use the shared AI service.

Consistent Logging

LLM usage can be measured consistently across the organization.

Provider Abstraction

Department applications remain insulated from much of the external provider integration detail.

Human-in-the-Loop: AI Proposes, Humans Commit

Reading information and changing business records have very different risk profiles. The platform therefore treats transactional requests differently from normal question answering.

User Request AI Draft Human Review Approve / Reject Database Commit

For create_record and update_record, the model receives the actual allowed_fields and required_fields for the target table. This constrains the draft to fields that genuinely exist in the application schema.

Inline Review

Proposed fields appear directly in the chat UI, where the user can inspect and edit them before selecting Approve or Reject.

Review Queue

Pending and historical tasks are available through a review queue so proposed AI actions remain visible and auditable.

Adjudication is intentionally different.
A re-adjudication represents a new decision event. Because claim_number is not unique in that table, the application inserts a new adjudication record rather than overwriting the previous decision.
MySQL 8.x Data Architecture

A single MySQL database provides common infrastructure without implying that every chatbot should freely access every department's information.

Database Object Architectural Responsibility

Architectural Principles Demonstrated
Separation of Concerns

Authentication, business logic, retrieval, LLM access and persistence are separate architectural responsibilities.

Least-Privilege Thinking

Department-specific access reduces the need for one universal chatbot to possess broad access across all healthcare domains.

Centralized AI Governance

External LLM traffic traverses a controlled shared integration point instead of being independently implemented ten times.

Identity Propagation

The original user's signed identity remains available when the chatbot calls the shared Gateway.

Human Accountability

AI can draft business changes, but higher-impact writes remain subject to explicit human approval.

Observability

HTTP activity, model activity, token usage, costs, latency and HITL decisions can be tracked rather than leaving AI behavior opaque.

The architecture in one sentence

Ten department-specific Python Flask AI applications use one Keycloak identity plane, perform their own department-scoped retrieval, access Anthropic through one controlled Central LLM Gateway, persist operational and business information in one logically segmented MySQL 8 platform, and place a human approval boundary in front of consequential data changes.
