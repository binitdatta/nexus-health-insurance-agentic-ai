Self-Hosting an Open-Source LLM with Ollama: What It Actually Costs

Understand model-size-to-VRAM relationships.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Learning Objectives
Understand model-size-to-VRAM relationships.
Understand why 70B-class models may require A100/H100-class memory footprints even when quantized.
Compare per-token managed API economics with fixed GPU infrastructure costs.
Understand that self-hosting shifts responsibility rather than eliminating it.
Model Sizing
7B–13B models can fit comfortably on smaller GPUs but may not match the structured tool-use reliability required by this platform.
32B-class models typically need materially more VRAM.
70B-class models can require roughly 40–48 GB or more when quantized, making A100 80GB/H100-class hardware practical evaluation targets.
Large MoE models can require even more memory.
Operational Costs Beyond GPU Rent
OS and driver patching.
Inference-runtime and container hardening.
Network segmentation and TLS.
Secrets, certificates, and key management.
Monitoring, alerting, backups, capacity planning, and incident response.
Model artifact provenance and vulnerability management.
Evaluation Requirement
Do not assume an open model is an equivalent replacement for Claude for forced tool-use.
Benchmark structured output validity, tool selection accuracy, latency, concurrency, hallucination rate, and recovery behavior against your actual workflows.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
