The Central LLM Gateway Pattern: One Chokepoint for Cost, Audit, and Control

Understand the Gateway as a policy and integration boundary rather than a RAG service.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Learning Objectives
Understand the Gateway as a policy and integration boundary rather than a RAG service.
Explain why centralizing external LLM access reduces credential sprawl.
Understand how central logging enables organization-wide cost, latency, and usage reporting.
Explain how the Gateway preserves user and department context.
Responsibilities of the Gateway
Validate incoming authenticated requests.
Enforce department consistency between token claims and request metadata.
Mediate access to the external LLM provider.
Normalize request/response handling.
Record LLM usage, latency, token counts, and cost.
Provide one place for future provider abstraction, rate limiting, guardrails, and policy.
What the Gateway Must Not Become
It should not receive direct broad access to every department business table.
It should not become a universal enterprise RAG layer with unrestricted cross-department retrieval.
It should not erase the identity of the original human user.
It should not become a hidden place where PHI-rich prompts are logged without equivalent access controls.
Architectural Result
Ten applications can evolve independently while one shared AI control point remains governable.
Changing the model provider can be isolated primarily to the Gateway rather than ten department codebases.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
