Human-in-the-Loop: Letting an LLM Propose Writes Without Letting It Write

Distinguish read-only AI assistance from consequential transactional writes.

Platform context: this topic is grounded in the Nexus architecture: ten department-scoped Python Flask chatbots, one Keycloak 26 central realm, one Central LLM Gateway on port 8000, Anthropic as the external LLM provider, and one MySQL 8.x platform with department-specific data, RAG knowledge, audit logs, HITL tasks, and cost summaries.
Learning Objectives
Distinguish read-only AI assistance from consequential transactional writes.
Understand why the LLM should draft rather than directly commit.
Explain allowed_fields and required_fields as schema constraints.
Understand inline approval and review-queue patterns.
HITL Flow
The user requests a create or update operation.
The chatbot determines intent and retrieves any required context.
The Gateway/LLM produces a structured draft constrained to actual database fields.
The proposed record is stored as a pending HITL task.
A human reviewer can inspect, edit, approve, or reject it.
Only after approval does application code perform the database write.
Why Schema-Constrained Drafting Matters
Passing allowed_fields prevents the model from inventing columns that cannot be persisted.
Passing required_fields ensures important business attributes are not silently omitted.
Validation remains deterministic application logic rather than a prompt-only instruction.
Adjudication Exception
Not every domain table has the same update semantics.
Re-adjudication is a new decision event, so claim_number need not be unique and a new row can be inserted rather than overwriting the prior decision.
HITL design must follow business semantics, not a universal CRUD shortcut.
Suggested Demonstration

Use the live platform while teaching this topic. Show the relevant department application, then trace the request through the architecture rather than explaining the concept only from slides.
